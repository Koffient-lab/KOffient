# Как мы измеряли модели

Этот документ описывает, как получены все цифры, на которых основан выбор модели для MVP: что меряли,
чем, в каких условиях и почему этим цифрам можно доверять. Сам выбор — в [SELECTION.md](SELECTION.md),
карточки выбранных моделей — [granite-4.0-1b.md](granite-4.0-1b.md) и [qwen3-0.6b.md](qwen3-0.6b.md).

Код всех измерений — пакет [`tooling/`](../../tooling/README.md). Движок везде один: llama.cpp тег `b12199`
(коммит `372dc5c`), формат GGUF.

## 1. Что нам нужно от модели

Сценарии мобильного ассистента и их роли в решении:

| Сценарий | Роль | Почему |
|---|---|---|
| Вызов функций, JSON по схеме | основной | на нём строится интеграция приложения с моделью |
| Следование инструкциям | основной | формат и ограничения ответа |
| Суммаризация переписки | вторичный | частая пользовательская задача |
| Математика, знания | контрольный | проверка, что модель не «сломана» сжатием |

Языки — английский и русский, каждый сценарий меряется на обоих. Одного сводного числа нет: оно скрыло бы,
где именно модель проседает. Варианты одной модели сравниваются при равном бюджете памяти («качество
против размера»).

Ограничения телефона: модель целиком в оперативной памяти (у массовых телефонов 6–8 ГБ, из них приложению
доступно 2–3), генерация на процессоре (на телефоне она упирается в пропускную способность памяти).

## 2. Качество: быстрый набор

### Задачи

| Задача | Сценарий | Примеров | Оценка | Источник |
|---|---|---|---|---|
| `bfcl-en`, `bfcl-ru` | вызов функций | 300 | сравнение вызова с эталоном проверяющим кодом BFCL | BFCL v3 и его русский перевод RFCB |
| `jsonschema` | JSON по схеме | 200 | ответ проходит валидацию по схеме | JSONSchemaBench |
| `ifeval-en`, `ifeval-ru` | инструкции | 300 | правила IFEval, строгий режим | IFEval и его русский перевод |
| `samsum-en`, `samsum-ru` | суммаризация | 200 | ROUGE-L | SAMSum и машинный перевод |
| `mgsm-en`, `mgsm-ru` | математика | 250 | совпадение итогового числа | MGSM |
| `mmlu-en`, `mmlu-ru` | знания | 285 | выбор буквы A–D | MMLU, ruMMLU (MERA) |

Подвыборки фиксированы и зависят только от идентификатора примера; английский и русский варианты одной
задачи содержат одни и те же примеры. Ревизии всех наборов закреплены — список в `tooling/README.md`.
Наборы в репозиторий не кладём (у части нет лицензии или она запрещает производные работы); они
используются только для внутренних замеров.

### Протокол

- Запрос идёт через `llama-server` тем же шаблоном чата, что лежит в GGUF модели (как будет в SDK).
- Генерация жадная: температура 0, все штрафы выключены и **заданы явно** в каждом запросе (почему это
  важно — раздел 9).
- У моделей с режимом рассуждений (Qwen3) он выключен: все модели отвечают в одинаковом режиме.
- **Подсказки задач не подгоняются под модель** после того, как увидели результат. Подсказка, подобранная
  под одну модель, измеряла бы подсказку, а не модель, и давала бы этой модели фору в сравнении.
- Ответы генерирует пул независимых серверов, у каждого один слот. Если дать одному серверу несколько
  слотов, запросы считаются одним пакетом, и ответ на запрос начинает зависеть от соседей по пакету: на одной
  выборке точность менялась от прогона к прогону. С пулом ответы повторяются побайтно.
- Каждый ответ сохраняется вместе с оценкой (`answers.jsonl`), поэтому любую цифру можно перепроверить по
  ответам.

### Правила чтения цифр

- **Вызов функций без группы «вызов не нужен».** В BFCL есть примеры, где правильно не вызывать функцию.
  Сжатая модель, которая просто реже вызывает функции, получает за них баллы и выглядит лучше исходной.
  В заголовочную оценку идут 240 примеров из 300; группа (60 примеров) показывается отдельным столбцом
  «без лишнего вызова» — она важна для продукта: модель, которая вызывает функцию без нужды, требует
  проверки вызова в приложении.
- **«Задача не различает варианты».** Если исходная модель выше уровня угадывания меньше чем на 0,10
  (угадывание: 0,25 для выбора из четырёх, 0 для остальных), сравнивать её сжатые варианты по этой задаче
  бессмысленно: при 200–300 примерах доверительный интервал — от ±0,04 до ±0,07.
- **Обрывы по лимиту длины** сохраняются в записи каждого прогона; заметные (больше 5%) указаны в карточках
  моделей. Оборванный ответ оценивается как есть.
- **Доверительный интервал 95%** — Вильсона для 0/1-оценок. Для вариантов одной модели (и для пары
  финалистов) дополнительно смотрим, у скольких примеров сменился вердикт и в какую сторону (парное
  сравнение, двусторонний биномиальный тест по изменившимся примерам). Задач девять, поправку на
  множественные сравнения не делаем, поэтому одиночное p около 0,03–0,05 считаем пограничным.
- **Ответ, который движок не смог разобрать как вызов функции**, — ошибка модели (оценка 0). Упавший запрос
  — ошибка прогона: задача целиком считается неудачной и пересчитывается.

## 3. Близость к исходной модели

Для каждого сжатого варианта: perplexity и KL-расхождение распределения следующего токена с исходной
моделью (bf16/fp16), плюс доля совпадений самого вероятного токена. Тексты — 40 фрагментов по 512 токенов:
тестовая часть WikiText-2 (английский) и 40 статей русской Википедии. Инструмент — `llama-perplexity`.

Близость дешёвая (минуты) и хорошо ловит грубые поломки, но **не заменяет задачи**: у Granite при KL 0,10
значимо просели только две русские задачи из девяти, у другой модели при KL 0,42 вызов функций упал с 0,77
до 0,33; калибровка imatrix заметно улучшила KL Granite, но не задачи. Решения принимаются по задачам.

## 4. Скорость и память

Раннер `bench run` заливает сборку движка и модель на Android-устройство через adb и меряет:

| Метрика | Чем |
|---|---|
| Скорость обработки промпта (256 и 1024 токена), генерации (128 токенов) | `llama-bench`, 5 повторов, медиана |
| Время до первого токена (короткий вопрос 272–277 токенов и запрос с шестью функциями 1252–1274 токена, в зависимости от токенизатора) | `llama-completion` |
| Время загрузки, тёплое и холодное | `llama-completion` |
| Пик памяти процесса | `time -v` |

**Телефон: OnePlus 9R** — Snapdragon 870 (1 ядро Cortex-A77 3,19 ГГц + 3 × A77 2,42 ГГц + 4 × A55 1,8 ГГц),
7,5 ГБ LPDDR4X, Android 12. Сборка движка — `armv8.2-a+dotprod+fp16` (без `i8mm`, его у этого процессора нет).
Условия: телефон на кабеле USB, экран включён (режим разработчика «Не выключать экран»), фоновые приложения
закрыты, 4 потока на больших ядрах, загрузка без отображения файла. Протокол: 3 круга с чередованием моделей,
пауза 90 с между прогонами, медиана и разброс. Повтор первой модели в конце серии совпал с началом (промпт
43,0 против 42,9 ток/с, генерация 19,7 против 19,0) — дрейфа от нагрева или батареи нет.

Сначала, до появления телефона, те же замеры делались **в эмуляторе Android x86_64** (4 ядра, AVX2). На
телефоне генерация оказалась медленнее эмулятора в 2 раза, а обработка промпта — в 4,5–5 раз, так что
эмулятор годится только для сравнения моделей между собой.

**Ограничение частоты.** Под нагрузкой большие ядра 9R работают на ~73% максимальной частоты (средние 1,77
ГГц из 2,42, главное 2,36 из 3,19), и это не зависит от числа нагруженных ядер и не связано с нагревом
(корпус холодный, механизмы охлаждения не включены). В настройках телефона выключен режим высокой
производительности OnePlus; влияние этого режима и запуска из adb, а не из приложения, не проверено. Все
телефонные цифры получены при этом ограничении.

**Память** меряется при загрузке модели без отображения файла в память (`load_mode = none`): с отображением
движок держит в памяти и страницы файла, и перепакованную копию весов, и пик процесса у Granite на 55% выше
(1950 против 1258 МБ в эмуляторе). Страницы файла система может вытеснить, так что этот пик завышает
реальную нагрузку. Кэш внимания растёт с контекстом: расчёт (80 КБ на токен у Granite, 112 КБ у Qwen3 в
fp16) подтверждён на телефоне — переход с контекста 2048 на 4096 добавил 175 и 235 МБ (расчёт 160 и 224).

## 5. Кэш промпта

Запрос приложения с функциями — около 1300 токенов, из них ~1240 одинаковы в каждом запросе (системный
промпт и описания функций). Замер того, как это будет в SDK: на телефоне запускается `llama-server` (модель
загружена один раз и остаётся в памяти), запрос идёт через шаблон чата модели (`--jinja`), ответ — один
токен, время берётся из таймингов сервера:

1. **Холодный запрос** — весь промпт считается с нуля.
2. **Следующие запросы** с тем же началом и другим вопросом — сервер переиспользует посчитанное начало и
   читает только новый вопрос (17–23 токена).
3. **Сохранение и восстановление** — состояние сохраняется в файл, сбрасывается и поднимается из файла
   (как после перезапуска приложения), затем снова задаётся вопрос.

Каждый вариант (модель × тип кэша внимания) — на отдельном сервере. Тот же эффект отдельно проверен через
`llama-completion --prompt-cache` (кэш в файле, процесс на каждый запрос).

## 6. Как распределяется нагрузка на телефоне

- **Масштаб по потокам:** `llama-bench` на 1–4 потоках, привязанных к большим ядрам (`taskset`), и на 4–8
  потоках без привязки (с малыми ядрами).
- **Настройки движка:** размер пакета (128/256/512), flash attention, режим ожидания потоков (`--poll`),
  жёсткая привязка к ядрам (`--cpu-strict`), приоритет.
- **Профиль:** штатный профилировщик Android `simpleperf` (по таймеру, 4000 Гц) поверх `llama-bench`,
  отдельно обработка промпта и генерация; отчёты по потокам и по функциям (бинарник собран с символами).
- **Частоты:** снимки частот ядер и теплового статуса во время замеров и короткие тесты холостой нагрузки.

## 7. Как выбирался рецепт квантования

Варианты одной модели сравниваются **попарно на одних и тех же примерах** (у скольких примеров вердикт стал
хуже и у скольких лучше, двусторонний биномиальный тест) — так видны изменения меньше ширины интервалов.
Сравнения ведутся внутри одного движка: ответы процессора и видеокарты на отдельных примерах расходятся
(раздел 10). Чтобы отделить эффект одного изменения, файлы собираются так, чтобы различаться только им:
`Q4_0` с калибровкой и без неё (одинаковые типы тензоров); кандидат и тот же рецепт с другим типом таблицы
словаря. Скорость каждого кандидата меряется на телефоне в одной серии с чередованием.

## 8. Как сделаны файлы моделей

Мы не берём готовые GGUF, а собираем свои — так известно, что именно в файле:

1. **Исходник** скачивается с Hugging Face в закреплённой ревизии, контрольные суммы сверяются с указанными в
   репозитории.
2. **Конвертация** в GGUF — штатным скриптом llama.cpp той же версии, что и движок, в отдельном окружении с
   закреплёнными версиями. Сразу после конвертации веса сверяются с исходником (расхождение — только
   округление fp16, порядка 10⁻⁸).
3. **Квантование** — `llama-quantize` той же версии. Рецепт (тип и переопределения) входит в имя файла.
4. Каждый шаг пишет **паспорт сборки**: откуда вход, чем и с какими параметрами собрано, контрольная сумма
   результата. Записи измерений находят свою сборку по sha256 файла, поэтому цепочка «Hugging Face → файл →
   цифры» прослеживается.

Зачем это нужно, показал первый же шаг: официальный «fp16» GGUF Qwen2.5 оказался не исходной моделью. По
виду весов (перенесённые между матрицами масштабы, обрезанные крайние значения) это похоже на предобработку
AWQ; прямого подтверждения от производителя нет. Наш fp16 совпал с исходными весами с точностью до
округления fp16 и имел perplexity ниже официального (13,76 против 14,15), а наш `q4_k_m` оказался на 93 МБ
меньше официального и ближе к исходной модели. Вторая находка: при связанной таблице словаря файл может
хранить её дважды. У Qwen2.5 официальные файлы хранят копию, а наша конвертация — нет. У Qwen3 копию
переносит и штатный конвертер, потому что она лежит в исходном чекпойнте отдельным тензором. Её убирает
наш шаг `model tie-output`: он проверяет, что копия побайтно равна таблице.

## 9. Что пошло не так и как это исправлено

Ниже ошибки, найденные по ходу. Каждая была найдена проверкой — сверкой с исходником, ручным разбором
ответов или независимым ревью — и после исправления затронутые цифры пересчитаны.

| Что | Как проявилось | Что сделано |
|---|---|---|
| GGUF несёт умолчания генерации производителя (например, штраф за повторы 1,1), и сервер применяет их, если запрос их не задаёт | наш `q4_k_m` Qwen2.5 был хуже официального на JSON (0,40 против 0,575): у нас считалось со штрафом, у официального — без | все параметры генерации задаются явно в каждом запросе; затронутые прогоны пересчитаны. Разрыв сократился до 0,04–0,07 (0,505 на процессоре, 0,535 на видеокарте) — в пределах интервала, но штраф объяснил не всю разницу |
| Кэш промптов и контрольные точки состояния в `llama-server` | у гибридной LFM2 (свёрточные слои) ответы вырождались в повтор одного токена; сервер занимал до 6,5 ГБ памяти | обе функции выключены (запросы и так считаются с нуля). У модели только с вниманием (Qwen2.5 `q4_k_m`) ответы с ними и без побайтно одинаковы (850 из 850) |
| Falcon-H1 на видеокарте | ответы вырождались и после выключения кэшей; причину не нашли | все его прогоны на видеокарте признаны недействительными; модель посчитана на процессоре (там вырождения нет) |
| Серверы на видеокарте под Windows падали с «out of memory» при свободной видеопамяти | упавшие запросы засчитывались как неверные ответы | упавший сервер перезапускается, запрос повторяется (ответ детерминирован — проверено 600 из 600 побайтно); задача с непрошедшими запросами считается неудачной |
| Granite в fp16 и некоторых типах квантования | в fp16 модель выдаёт NaN; тип Q4_1 (его `llama-quantize` ставит при калибровке) ломает модель полностью; на видеокарте 3-битные типы дают NaN. Вероятная причина — активации выходят за предел fp16 (гипотеза, не доказана) | Granite считается в bf16 и K-квантах; Q4_1 для неё запрещён (Q5_1 не проверяли); 3-битные варианты считались на процессоре |
| Логиты базы с NaN | близость к fp16-базе Granite посчиталась по NaN-логитам, и записи сохранились как успешные | логиты базы пишутся во временный файл и принимаются только после проверки; такие записи признаны недействительными, близость Granite пересчитана от bf16 |
| Разбор чисел в `mgsm-ru` | ответ вида «8,956,25» ронял оценку всей задачи | разбор чисел со смешанными разделителями; неразборчивое число — неверный ответ, а не падение |
| Спекулятивное декодирование «в 3–6 раз медленнее» | так было записано по одному прогону; ревью показало аномалию в замере | вывод отозван; надёжного замера нет, ускорения единичный замер не показал |
| «Калибровка imatrix возвращает качество исходной модели» | так было записано по таблице; парное сравнение в ревью показало значимое падение MMLU против bf16 | вывод исправлен: калибровка улучшает близость; против обычного `q4_k_m` значимых различий на задачах нет |
| «Генерация на телефоне упирается в пропускную способность памяти» | так предполагалось по литературе; на 9R генерация растёт почти линейно с 1 до 4 потоков | гипотеза опровергнута для этого телефона: генерация упирается в вычисления, поэтому важны частота ядер и тип квантования |
| «`Q4_0` лучше `Q4_K_M` на русском вызове функций» | так было сформулировано по одному p = 0,007 | при девяти задачах это не проходит поправку на множественные сравнения; `Q4_K_M` теряет против bf16, а `Q4_0` остаётся на её уровне, и `Q4_0` без калибровки даёт то же — вывод «не хуже», выбор по скорости |
| «Телефон перегрет и сбрасывает частоту» | тепловой статус Android 3 из 4 | статус выставлен датчиком ограничения тока батареи из кэша, корпус холодный, охлаждение не включено; потолок частоты — не от нагрева (раздел 4) |
| Опыты на телефоне стартовали раньше времени | скрипт ждал строку «all done» в журнале серии, а её туда записал пробный запуск | ~2 минуты наложились на один прогон серии; он помечен недействительным (`invalid.jsonl` по `run_id`) и повторён; сборщик пакета такие прогоны пропускает |
| Опыт с кэшем промпта: зависание и чужой сервер | фоновый `llama-server` держал ввод `adb shell` (25 минут ожидания); остановка по полному пути не совпадала с `./llama-server`, первый сервер остался на порту и отвечал на следующие замеры | ввод отвязывается, сервер останавливается по имени, перед запуском проверяется, что порт свободен; три испорченных варианта перемерены |

После каждой серии экспериментов результаты и код проверял независимый проверяющий, которому давали код,
команды и сырые данные без наших выводов. Два наших вывода он опроверг (строки про спекулятивное
декодирование и калибровку). Эти документы тоже прошли такую проверку: все цифры сверены с сырыми записями.
По её итогам ослаблены выводы, которые были сильнее данных: «Granite сжимается без потерь», отказ от imatrix,
отсев Falcon-H1. Добавлена доля лишних вызовов функций.

## 10. Процессор и видеокарта

Качество большинства кандидатов посчитано на видеокарте (CUDA-сборка той же версии) — на процессоре один
вариант 1B-модели занимал 2–3 часа. Сверка на одном файле: средние оценки процессора и видеокарты совпадают
в пределах интервалов (разница до 0,04), но отдельные ответы расходятся (вердикт меняется у 1–10% примеров).
Поэтому средние оценки с двух движков сравнимы, а «доля изменившихся ответов» — только внутри одного движка.
Телефон считает на процессоре.

## 11. Ограничения

- **Один телефон** (OnePlus 9R, Snapdragon 870) и замеры через adb, а не из приложения. Частота ядер при
  этом ограничена ~73% максимума (раздел 4). Скорость на других телефонах — оценка.
- Быстрый набор — 200–300 примеров на задачу: по интервалам различает разницу между моделями от ~0,1;
  меньшие изменения у вариантов одной модели видны только в попарном сравнении.
- Русские наборы для суммаризации — машинный перевод; русский язык для Granite официально не заявлен
  производителем, его качество — только наши замеры.
- Свободная генерация (чат) не оценивалась судьёй-моделью; это план полного набора для финалистов.

## 12. Как воспроизвести

```
# сборка файла
python -m koffient_tooling model fetch    --work-dir <папка> --repo ibm-granite/granite-4.0-1b --revision 6a7381ba1f54d684ff508d991aeb7dc580157103
python -m koffient_tooling model convert  --work-dir <папка> --source-dir <папка>/sources/granite-4.0-1b/6a7381b --name granite-4.0-1b
#   Granite: калибровка (400 фрагментов по 512 токенов, английский и русский текст, не пересекается с наборами
#   оценки) и Q4_0 с таблицей словаря в Q4_0; ffn_down явно в Q4_0 (иначе llama-quantize ставит Q4_1, ломающий Granite)
python -m koffient_tooling model imatrix  --work-dir <папка> --input <bf16.gguf> --calibration <тексты> --chunks 400
python -m koffient_tooling model quantize --work-dir <папка> --input <bf16.gguf> --type q4_0 --imatrix <imatrix.gguf> --tensor-type ffn_down=q4_0 --embedding-type q4_0
#   Qwen3: убрать копию таблицы словаря, затем Q4_K_M
python -m koffient_tooling model tie-output --work-dir <папка> --input <qwen3-f16.gguf>
python -m koffient_tooling model quantize --work-dir <папка> --input <qwen3-tied-f16.gguf> --type q4_k_m

# качество и близость (--gpu-layers 99 и CUDA-сборка движка — на видеокарте, как большинство наших прогонов)
python -m koffient_tooling quality run       --work-dir <папка> --model <gguf> [--gpu-layers 99]
python -m koffient_tooling quality closeness --work-dir <папка> --model <gguf> --base <bf16.gguf> [--gpu-layers 99]

# скорость и память на устройстве
python -m koffient_tooling bench run --work-dir <папка> --model <gguf> --build <сборка> --load-mode none [--prompt-file ttft_tools_en.txt]

# пакет для SDK
python -m koffient_tooling model package --work-dir <папка> --model <gguf> --role primary
```

Что должно лежать в рабочей папке (наборы данных, сборки движка) — в [`tooling/README.md`](../../tooling/README.md).
Скрипты опытов на телефоне (потоки, настройки движка, кэш промпта, профиль, частоты, выбор рецепта) и
попарной проверки качества — в [`tooling/experiments/`](../../tooling/experiments/README.md), в том виде, в
котором они запускались.
